# 功能模块业务节点详细设计

> 本文档是《简历智能体产品需求文档》第 5 章与《模块 Agent 工作流模式设计》的落地细化，逐节点定义每个业务节点的处理内容、输入数据类型、输出数据格式、处理规则与异常边界。数据契约与《前端数据接口设计》《模块 Agent 工作流模式设计》保持一致。

## 0. 约定

### 0.1 编排范式与设计模式

| 模块 | 编排范式 | 设计模式 |
|------|----------|----------|
| 简历解析引擎 | 串行链（Pipeline） | 交接模式（Handoff） |
| 简历智能问答 | 路由（Router）+ RAG | 路由模式 + SKILL |
| 简历智能生成与优化 | ReAct + 串行链 | 交接模式 + SKILL |
| 用户中心与数据管理 | 标准 CRUD | 状态管理 |

### 0.2 节点间传递的数据契约

- 简历解析引擎输入 `简历文件`，输出 `StructuredResume`，是问答与优化两模块的唯一数据来源。
- 字段统一以 `value + confidence` 包装；解析后单独输出 `pending` 待确认清单。
- 节点间传递统一使用 Pydantic 模型（后端）承载状态，节点函数签名统一为 `(state) -> dict`，返回增量字段合并回状态。

### 0.3 统一响应（前端）与错误码

参见《前端数据接口设计》第 0 章。错误码前缀：`PARSE_*` / `QA_*` / `EDIT_*` / `USER_*`。

## 1. 简历解析引擎（F-PARSE-001 ~ F-PARSE-004）

**业务节点**：文件校验 → 多格式解析 → 复杂排版还原 → 结构化信息提取 → 解析结果校验与补全

### 1.1 节点一：文件校验

- **对应需求**：F-PARSE-001（文件校验部分）
- **节点职责**：解析前校验文件合法性，任一校验失败即中断流水线。

**处理内容（三个角度）**

| 校验角度 | 处理内容 |
|----------|----------|
| 格式校验 | 基于字节流头部魔数识别真实格式，与支持格式比对 |
| 加密校验 | 检测文件是否加密，加密则拦截 |
| 损坏校验 | 检测文件是否为空、不可读、头部异常或格式声明与魔数不符 |

**输入数据类型**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `file_data` | bytes | 是 | 网络传输的原始字节流 |
| `file_name` | string | 否 | 源文件名，仅作展示 |
| `content_type` | string | 否 | 客户端声明类型，仅作「声明 vs 实际」比对参考 |

**输出数据格式**

成功：

```json
{
  "file_valid": true,
  "file_type": "pdf",
  "error": null
}
```

失败（任一校验不通过即返回，不继续后续节点）：

```json
{
  "file_valid": false,
  "file_type": null,
  "error": {
    "code": "PARSE_FORMAT_ERROR",
    "message": "文件格式错误，请重新上传"
  }
}
```

**错误码映射**

| 校验项 | 错误码 | 用户提示 |
|--------|--------|----------|
| 格式不合法 | `PARSE_FORMAT_ERROR` | 文件格式错误，请重新上传 |
| 加密 | `PARSE_ENCRYPTED` | 文件已加密，请解除加密后上传 |
| 损坏 | `PARSE_CORRUPTED` | 文件已损坏，请重新导出后上传 |
| 空文件 | `PARSE_EMPTY` | 文件为空，请重新上传 |

**支持格式与魔数**

| 格式 | 魔数（十六进制） |
|------|------|
| PDF | `25 50 44 46 2D`（`%PDF-`） |
| DOCX | `50 4B 03 04`（`PK`） |
| DOC | `D0 CF 11 E0 A1 B1 1A E1`（OLE） |
| PNG | `89 50 4E 47` |
| JPEG | `FF D8 FF` |

### 1.2 节点二：多格式解析

- **对应需求**：F-PARSE-001
- **节点职责**：将字节流解析为可读文本，按格式分派解析器；扫描件/图片走 OCR 兜底。

**处理内容**

| 格式 | 解析策略 |
|------|----------|
| PDF | 优先提取文本层（pdftotext 等价），文本为空或异常降级 OCR |
| DOCX | 解析 OOXML 提取段落文本 |
| DOC | 解析 OLE 提取文本（异常降级 OCR） |
| PNG/JPEG | 直接 OCR |

**输入数据类型**

```json
{
  "file_data": "bytes（原始字节流）",
  "file_type": "pdf",
  "file_valid": true
}
```

**输出数据格式**

```json
{
  "text": "保持阅读顺序的纯文本/半结构化文本",
  "ocr_used": false,
  "source_type": "pdf"
}
```

**处理规则与边界**

- 文本层提取失败或为空 → 触发 OCR（tesseract，大模型 OCR 兜底）。
- `ocr_used` 标记扫描件/图片，供下游置信度评估参考。
- 解析异常 → 返回 `PARSE_INTERNAL`，联系管理员。

### 1.3 节点三：复杂排版还原

- **对应需求**：F-PARSE-002
- **节点职责**：还原多栏/表格/嵌套结构/页眉页脚等的阅读顺序，输出结构化文本块。

**处理内容**

| 处理对象 | 处理逻辑 |
|----------|----------|
| 双栏/多栏布局 | 规则引擎识别栏边界，重建阅读顺序 |
| 表格 | 正则 + 规则引擎提取单元格，还原行列关系 |
| 嵌套结构 | 大模型文档理解能力做内容重构 |
| 页眉页脚/分割线/图标 | 识别并剥离或降级处理 |

**输入数据类型**

```json
{
  "text": "节点二输出的纯文本/半结构化文本",
  "source_type": "pdf",
  "ocr_used": false
}
```

**输出数据格式**

```json
{
  "blocks": [
    {
      "type": "heading",
      "text": "教育背景",
      "order": 3
    },
    {
      "type": "table",
      "text": "学校 | 专业 | 学历 ...",
      "order": 4,
      "cells": []
    },
    {
      "type": "paragraph",
      "text": "...",
      "order": 5
    }
  ]
}
```

**处理规则与边界**

- 输出块按 `order` 组织阅读顺序，作为结构化提取节点的输入。
- 版式过于复杂无法可靠还原时，降级交由大模型文档理解重构。

### 1.4 节点四：结构化信息提取

- **对应需求**：F-PARSE-003
- **节点职责**：从结构化文本块中提取 200+ 字段，产出一致数据契约 `StructuredResume`。

**输入数据类型**

```json
{
  "blocks": "节点三输出的结构化文本块"
}
```

**输出数据格式**（即 `StructuredResume` 核心 `fields` + `pending` 预生成）

```json
{
  "fields": {
    "personal":   { "name": {"value": "张三", "confidence": 0.98}, "phone": {"value": "138...", "confidence": 0.97} },
    "education":  [ {"school": "XX大学", "major": "计算机", "degree": "本科", "confidence": 0.95} ],
    "experience": [ {"org": "XX公司", "role": "后端", "start": "2021-07", "end": "2024-06", "confidence": 0.92} ],
    "skills":     [ {"name": "Python", "confidence": 0.9} ],
    "awards":     [],
    "summary":    {"value": "...", "confidence": 0.85}
  },
  "pending": [
    { "field": "experience[1].end", "reason": "低置信度", "confidence": 0.55, "status": "待确认" }
  ]
}
```

**提取字段覆盖**

| 分类 | 字段 |
|------|------|
| 个人信息 | 姓名、联系方式、出生年月、政治面貌、所在城市 |
| 教育背景 | 学校、专业、学历、入学/毕业时间、GPA/成绩排名、主修课程 |
| 实践经历 | 实习/工作/社团/项目的时间段、公司/组织、职位/角色 |
| 技能证书 | 专业技能、语言能力、证书资质 |
| 获奖情况 | 奖学金、竞赛奖项、荣誉称号 |
| 个人评价 | 自我认知、职业规划 |

**处理规则与边界**

- 每个字段产出 `value + confidence`，置信度作为下游「待确认」判定依据。
- 目标解析准确率 ≥ 96%。
- 混合策略：规则引擎（正则/字段词典）优先，扫描件/低置信度交给大模型文档理解。

### 1.5 节点五：解析结果校验与补全

- **对应需求**：F-PARSE-004
- **节点职责**：校验解析结果完整性，标记低置信度/缺失字段，产出最终 `StructuredResume`。

**处理内容（三类校验）**

| 校验项 | 规则 |
|--------|------|
| 必填字段缺失检测 | 关键字段（姓名/联系方式等）缺失时提示补充 |
| 置信度阈值检查 | 低于阈值字段进入 `pending`，提示确认/修正 |
| 字段格式合法性 | 电话/日期/邮箱等格式校验，非法则标记 |

**输入数据类型**：节点四的 `fields` + 预生成的 `pending`。

**输出数据格式**（最终 `StructuredResume`，与《前端数据接口设计》1.1 一致）

```json
{
  "resume_id": "rsm_xxx",
  "source": { "type": "pdf", "ocr_used": false, "file_type": "pdf" },
  "fields": { "...": "同上" },
  "pending": [
    { "field": "experience[1].end", "reason": "低置信度", "confidence": 0.55, "status": "待确认" }
  ],
  "file_valid": true
}
```

**处理规则与边界**

- `pending` 状态：`待确认` → 用户确认后 `已确认`（对应接口 `PATCH /resumes/{id}/fields`）。
- 关键字段缺失 → 提示用户补充；系统错误 → 联系管理员。

## 2. 简历智能问答（F-QA-001 ~ F-QA-004）

**业务节点**：两个对等子图——模拟面试（agent=面试官，逐题交互）与面试辅导（agent=候选人，生成参考答案），共用检索（RAG）、记忆、LLM 三项运行时能力。

**编排范式**：路由（Router）+ RAG；**设计模式**：路由模式 + SKILL。

> 需求编号缺口：① 模拟面试的「逐题提问 → 追问/评估 → 面试报告」在 PRD 中无对应 F-QA 编号（现仅有 F-QA-001 面试问题自动生成）；② 面试辅导的「外部知识库 RAG 增强」在 F-QA-002 中未体现。以下按实现设计描述，编号缺口待 PRD 补充。

### 2.0 模块总览

```
问答模块 entry_router（按 request_type 分发，非 NLP）
├── mock_interview（模拟面试，agent=面试官）
└── coaching（面试辅导，agent=候选人）
        │
  共享运行时：SKILL 注册表 / RetrievalSkill / LLMClient / 记忆存储
```

| 维度 | 模拟面试 | 面试辅导 |
|------|----------|----------|
| agent 角色 | 面试官 | 候选人（模拟用户本人） |
| 对话方向 | agent 问 → 用户答 | 用户给面试题 → agent 作答 |
| 核心动作 | 逐题提问 → 追问/评分 → 总结报告 | 生成个性化参考答案 |
| 检索来源 | 简历内部（出题依据） | 简历内部 + 外部知识库（RAG 增强） |
| 对应接口 | `POST /questions`（扩展为面试会话） | `POST /qa` |

### 2.1 子图 A：模拟面试（mock_interview）

**节点**：上下文准备 → 难度分级 → 问题生成 → 提问 → 追问评估 → 总结报告

#### 2.1.1 节点一：上下文准备 context_prepare

- **节点职责**：取结构化简历、目标岗位 JD、岗位级别，校验经历充足性。

**输入数据类型**

```json
{
  "fields": "<StructuredResume.fields>",
  "jd": "岗位描述文本（可选）",
  "level": "中级"
}
```

**输出数据格式**

成功：`{ "context_ready": true }`

失败：`{ "error": { "code": "QA_NO_EXPERIENCE", "message": "简历信息不足，请补充关键经历后再开始模拟面试" } }`

**处理规则与边界**：`experience` 为空或关键经历缺失 → `QA_NO_EXPERIENCE`；未提供 JD → 基于简历生成通用问题。

#### 2.1.2 节点二：难度分级 difficulty_grading

- **对应需求**：F-QA-004
- **节点职责**：按岗位级别映射问题难度与深度，产出难度画像。

| 级别 | 难度标签 | 问题深度 |
|------|----------|----------|
| 初级 | 初 | 基础概念、工具使用、简单场景 |
| 中级 | 中 | 方案设计、问题解决、团队协作 |
| 高级 | 高 | 架构设计、技术选型、团队管理 |
| 专家 | 专家 | 技术战略、行业趋势、创新突破 |

- **输入**：`{ "level": "中级" }`
- **输出**：

```json
{
  "difficulty_profile": {
    "tag": "中",
    "depth": "方案设计/问题解决",
    "ratio": { "technical": 0.4, "behavioral": 0.3, "case": 0.3 }
  }
}
```

#### 2.1.3 节点三：问题生成 question_generate

- **对应需求**：F-QA-001
- **节点职责**：按难度画像生成技术/行为/案例三类面试问题。

- **输入**：`fields + jd + difficulty_profile`
- **输出**：

```json
{
  "question_list": {
    "technical":  [ { "id": "q1", "question": "...", "difficulty": "中", "references": ["experience[0]"] } ],
    "behavioral": [ { "id": "q2", "question": "...", "difficulty": "中", "references": [] } ],
    "case":       [ { "id": "q3", "question": "...", "difficulty": "中", "references": ["experience[1]"] } ]
  }
}
```

**处理规则与边界**：问题配比技术 40% + 行为 30% + 案例 30%；每条问题须关联简历具体经历/技能（`references`）。

#### 2.1.4 节点四：提问 ask

- **节点职责**：多轮状态机，从 `question_list` 逐题抛出下一题，驱动面试推进。

- **输入**：`question_list + 当前进度（已问/当前题）`
- **输出**：

```json
{
  "current_question": { "id": "q1", "question": "..." },
  "progress": { "asked": 1, "total": 10 },
  "status": "asking"
}
```

**处理规则与边界**：题目耗尽 → 进入总结节点；用户中断 → 提前进入总结。

#### 2.1.5 节点五：追问评估 evaluate

- **节点职责**：对用户作答进行追问、点评与评分。

- **输入**：`current_question + user_answer`
- **输出**：

```json
{
  "feedback": { "score": 82, "comment": "...", "follow_up": "追问内容（可选）" }
}
```

#### 2.1.6 节点六：总结报告 summarize

- **节点职责**：汇总全部作答与评分，生成面试评估报告。

- **输出**（`InterviewReport`）：

```json
{
  "report": {
    "session_id": "mock_xxx",
    "total_score": 80,
    "dimensions": { "technical": 78, "behavioral": 82, "case": 81 },
    "highlights": ["..."],
    "suggestions": ["..."],
    "qa_records": [ { "question": "...", "answer": "...", "score": 82 } ]
  }
}
```

### 2.2 子图 B：面试辅导（coaching）

**节点**：意图识别 → 双源检索 → 回答生成 → 记忆持久化

#### 2.2.1 节点一：意图识别 intent_recognition

- **对应需求**：F-QA-002（辅助）
- **节点职责**：理解用户提出的面试题类型，用于后续检索与回答策略。

| 意图类型 | 说明 |
|----------|------|
| 技术面 | 针对技术岗位的技术问题 |
| 行为面 | 基于 STAR 的行为问题 |
| 案例面 | 基于项目经历的案例问题 |
| 通用 | 其他通用问题 |

- **输入**：`{ "question": "介绍一下你最有挑战的项目" }`
- **输出**：`{ "intent": "案例面", "confidence": 0.91 }`

#### 2.2.2 节点二：双源检索 retrieval

- **对应需求**：F-QA-002
- **节点职责**：经 `RetrievalSkill` 接口检索简历内部字段 + 外部知识库，作为回答依据。

- **输入**：`question + intent + fields`
- **输出**：

```json
{
  "retrieved": [
    { "source": "resume", "field": "experience[0]", "text": "...", "score": 0.88 },
    { "source": "kb",     "field": "star_template", "text": "...", "score": 0.76 }
  ]
}
```

**处理规则**：`RetrievalSkill` 为统一接口，两个实现经 `SkillRegistry` 动态注册/替换；先落接口 + 桩，外部向量检索（Milvus）后续实现。

#### 2.2.3 节点三：回答生成 answer_generate

- **对应需求**：F-QA-002
- **节点职责**：agent 以候选人身份生成个性化参考答案，引用简历、禁止编造。

- **输入**：`question + intent + retrieved + 历史`
- **输出**（`AnswerReference`）：

```json
{
  "session_id": "sess_xxx",
  "answer": "...",
  "citations": ["experience[0]"]
}
```

**处理规则**：回答强制引用简历具体段落（`citations`）；无对应信息时如实说明，不编造。

#### 2.2.4 节点四：记忆持久化 memory_write

- **对应需求**：F-QA-003
- **节点职责**：写多轮对话上下文，敏感信息脱敏存储。

- **输入**：`question + answer + session_id + 历史`
- **输出**：更新后的会话记忆（对外不暴露脱敏前内容）。

### 2.3 检索设计（接口 + 动态 SKILL，双源）

```
RetrievalSkill.retrieve(question, intent, fields) -> retrieved[]
├── ResumeFieldRetrievalSkill    # 内部：简历字段定位检索（现在可做）
└── ExternalKBRetrievalSkill     # 外部：面试知识库向量检索（Milvus，后续实现）
```

`retrieved[]` 统一带 `source`（`resume`/`kb`）、`field`、`text`、`score`；`answer_generate` 据此区分「简历事实」与「知识增强」，保证引用可追溯、不编造。

### 2.4 错误码映射

| 场景 | 错误码 | 用户提示 |
|------|--------|----------|
| 简历信息不足 | `QA_NO_EXPERIENCE` | 简历信息不足，请补充关键经历后再试 |
| 简历未解析/缺失 | `QA_NO_RESUME` | 请先上传并解析简历 |
| 面试题为空 | `QA_NO_QUESTION` | 问题为空，请先输入面试题 |
| 检索无结果 | `QA_RETRIEVE_EMPTY` | 未找到相关信息，请换一种问法 |
| 系统错误 | `QA_INTERNAL` | 系统错误，请联系管理员 |

## 3. 简历智能生成与优化（F-EDIT-001 ~ F-EDIT-012）

**业务节点**：信息获取 → 简历生成/逐条优化（8 类 SKILL）→ 一键应用与对比

### 3.1 节点一：信息获取

- **对应需求**：F-EDIT-001
- **节点职责**：获取简历数据来源（复用 `StructuredResume` 或手动输入）。

**输入数据类型**

| 来源 | 数据 |
|------|------|
| 上传简历 | `StructuredResume`（复用解析引擎） |
| 手动输入 | 个人信息、工作经历、项目经历等表单数据 |

**输出数据格式**：统一的简历数据结构（字段同 `StructuredResume.fields`）。

### 3.2 节点二：简历生成 / 逐条优化（8 类 SKILL）

- **对应需求**：F-EDIT-002 ~ F-EDIT-008, F-EDIT-011, F-EDIT-012
- **节点职责**：ReAct 对每条建议执行「分析 → 生成 → 校验」，产出 `EditSuggestion[]`。

**各 SKILL 处理内容**

| SKILL | 对应需求 | 处理内容 |
|-------|----------|----------|
| SKILL-2 简历生成 | F-EDIT-002 | 依据输入生成整份简历 |
| SKILL-3 STAR 优化 | F-EDIT-003 | 检测并补全 STAR 四要素 |
| SKILL-4 量化成果 | F-EDIT-004 | 直接量化/相对量化/行业基准 |
| SKILL-5 关键词 | F-EDIT-005 | 基于 JD 做关键词覆盖对比 |
| SKILL-6 动词替换 | F-EDIT-006 | 被动词替换为主动动词 |
| SKILL-7 排版 | F-EDIT-007 | 字体/行距/层级/留白检测 |
| SKILL-8 ATS 检测 | F-EDIT-008 | 多栏/字体/表格/图片文字检测 |
| SKILL-9 段落优化 | F-EDIT-011 | 分段落分析建议 |
| SKILL-10 长度优化 | F-EDIT-012 | 篇幅诊断与删减/补充建议 |

**输入数据类型**

```json
{
  "resume": "<StructuredResume 或手动输入>",
  "jd": "岗位描述（可选）",
  "optimize_types": ["star", "quantify", "..."]
}
```

**输出数据格式**（`EditSuggestion[]`）

```json
{
  "suggestions": [
    {
      "id": "sug_001",
      "type": "STAR",
      "target": { "field": "experience[0]", "text": "原文块" },
      "before": "负责后端开发工作",
      "after": "作为后端负责人主导XX系统从0到1搭建...",
      "explain": "补全了结果量化，缺失Result要素",
      "location": "experience[0]",
      "priority": "high"
    }
  ]
}
```

**处理规则与边界**

- 未提供 JD → 关键词/ATS 降级为通用规则。
- 简历为空或信息严重不足 → `EDIT_EMPTY_RESUME`。
- 每条建议可追溯（原文 → 优化后）。

### 3.3 节点三：一键应用与对比

- **对应需求**：F-EDIT-009, F-EDIT-010
- **节点职责**：应用优化建议生成新版本，支持回退与对比。

**输入数据类型**

```json
{ "suggestion_ids": ["sug_001"], "accept_all": false }
```

**输出数据格式**

```json
{ "version": "v2", "resume_id": "rsm_xxx", "updated_fields": "..." }
```

**处理规则**

- 每次优化生成新版本号，支持回退与对比。
- `accept_all=true` 忽略 `suggestion_ids`。
- 保留优化日志，支持回退到优化前版本。
